# Release Management

This document describes how releases of this integration are built and published.

## Overview

Releases are fully automated with [release-please](https://github.com/googleapis/release-please), which bumps the version and writes the changelog from the [Conventional Commits](https://www.conventionalcommits.org/) on `main`. An optional local script can enhance the release notes using GitHub Copilot CLI.

**Version source of truth:** `custom_components/sensus_analytics/manifest.json` (kept in sync with `.release-please-manifest.json`)

## How It Works

### The Release Cycle

```text
1. A pull request is squash-merged into main
   (its title is a Conventional Commit, e.g. "fix: ...")
        ↓
2. release-please opens or updates a release PR
        ↓
3. The workflow enables auto-merge on the release PR
        ↓
4. Required checks pass (CodeQL, Ruff, Hassfest validation, HACS validation)
   and the release PR merges on its own
        ↓
5. release-please creates the Git tag and GitHub Release
        ↓
6. HACS picks up the new release
```

### Pull Request Titles

Pull requests are squash-merged, so **the PR title becomes the commit message on `main`**. release-please reads only those commit messages, so the PR title must be a Conventional Commit (for example `fix: handle empty hourly usage data`). The individual commit messages inside the PR branch don't matter.

### The Release PR

After a `feat`, `fix`, or `perf` commit reaches `main`, release-please opens a pull request titled:

```text
chore(main): release X.Y.Z
```

The PR:

- Has the label `autorelease: pending`
- Contains an updated `CHANGELOG.md` (prepended section for the new version)
- Contains the version bump in `manifest.json` and `.release-please-manifest.json`
- Is updated automatically as more commits land on `main`
- Has auto-merge enabled by the workflow, so it merges once the required checks pass

The workflow uses the `RELEASE_PLEASE_TOKEN` secret (a personal access token) so the release PR triggers CI. Pull requests opened with the default `GITHUB_TOKEN` never start other workflows, so the required checks would never run and the release PR would not merge on its own.

To hold a release, disable auto-merge on the release PR. It stays open and keeps collecting changes until it is merged.

### Version Bumping Rules

The project is past `1.0.0`, so standard SemVer applies:

| Commit type                                     | Version change                      |
| ----------------------------------------------- | ----------------------------------- |
| `fix`, `perf`                                   | patch bump (e.g. `1.2.3` → `1.2.4`) |
| `feat`                                          | minor bump (e.g. `1.2.3` → `1.3.0`) |
| `feat!`, `fix!`, or a `BREAKING CHANGE:` footer | major bump (e.g. `1.2.3` → `2.0.0`) |
| `chore`, `ci`, `docs`, `test`, `refactor`       | no release                          |

### What Appears in the Changelog

`CHANGELOG.md` is generated by release-please, so don't edit it by hand. It is excluded from Prettier and markdownlint. Only user-facing changes appear in it:

| Type                                      | Visible        |
| ----------------------------------------- | -------------- |
| `feat`                                    | ✅ Features    |
| `fix`                                     | ✅ Bug Fixes   |
| `perf`                                    | ✅ Performance |
| `refactor`, `chore`, `docs`, `test`, `ci` | hidden         |

## Developer Scripts

### `script/version`

Reads the canonical version from `manifest.json`.

```bash
./script/version              # Print the current version, e.g. 1.2.3
./script/version --tag        # Print: v1.8.1
./script/version --check      # Verify manifest.json matches .release-please-manifest.json
```

### `script/release-notes`

Generates AI-enhanced release notes using [GitHub Copilot CLI](https://docs.github.com/en/copilot/concepts/agents/about-copilot-cli). Requires an active Copilot subscription and `gh auth login`.

```bash
# Preview enhanced notes on stdout
./script/release-notes

# Update the open release-please PR body with enhanced notes
./script/release-notes --apply

# Launch Copilot CLI interactively with context pre-loaded
./script/release-notes --interactive
```

**How it works:**

1. Finds the open release-please PR (`autorelease: pending` label)
2. Collects rich context since the last tag:
   - Full commit details (subject, body, per-commit file stats)
   - Compact code diff for user-facing paths (sensors, config flow, services, translations)
   - Net file change list as source of truth
   - Revert commit list as chronology hints
3. Builds a detailed prompt with audience definition, jargon rules, and file impact guidance
4. Sends everything to Copilot CLI via stdin (avoids shell-escaping issues with large prompts)
5. Outputs the result to stdout, or updates the PR body with `--apply`

**`--interactive` mode** writes the full prompt and context to `.ai-scratch/release-notes-context.md` and launches a Copilot CLI session so you can iterate manually.

**Skip a commit from release notes** by adding a trailer to the commit body:

```text
Release-Notes: skip
```

or:

```text
User-Impact: none
```

**Environment variables:**

| Variable                 | Default             | Description                     |
| ------------------------ | ------------------- | ------------------------------- |
| `COPILOT_MODEL`          | `claude-sonnet-4.6` | AI model to use                 |
| `RELEASE_NOTES_DIFF_MAX` | `8000`              | Max bytes for code diff context |

## Typical Release Workflow

### Automated (default)

1. Open a pull request with a Conventional Commit title, for example `feat(sensor): add weekly usage sensor`.
2. Squash-merge it into `main` once CI passes.
3. release-please opens or updates the release PR. It merges itself when its checks pass, and the release is published.

### With enhanced release notes

Run these while the release PR is open. Disable auto-merge on it first if you need more time.

```bash
# 1. Check the current version
./script/version

# 2. Generate Copilot-enhanced release notes and review them
./script/release-notes

# 3. If satisfied, update the release PR body
./script/release-notes --apply
```

Then re-enable auto-merge (or merge the release PR yourself).

## GitHub Repository Setup (One-Time)

> [!NOTE]
> These settings cannot be stored in the repository — configure them once on GitHub.com.

### Actions Permissions

In **Settings → Actions → General → Workflow permissions**:

- Select **Read and write permissions**
- Enable **Allow GitHub Actions to create and approve pull requests**

### Auto-Merge

In **Settings → General → Pull Requests**, enable **Allow auto-merge**. Squash merging must be allowed too, because the workflow enables auto-merge with squash.

### `RELEASE_PLEASE_TOKEN` Secret

Create a fine-grained personal access token:

- **Repository access:** only this repository
- **Permissions:** Contents, Pull requests, and Issues — read and write

Add it under **Settings → Secrets and variables → Actions** as `RELEASE_PLEASE_TOKEN`. Without it the workflow falls back to `GITHUB_TOKEN`: the release PR is still opened, but it won't trigger CI, so it can't auto-merge.

### Branch Protection for `main`

In **Settings → Branches** (ruleset or classic protection rule for `main`):

- **Require a pull request before merging**
- **Require status checks to pass** — add `CodeQL`, `Ruff`, `Hassfest validation`, and `HACS validation` as required checks

The required checks are what gate the release PR's auto-merge, so a release with failing CI cannot go out.
